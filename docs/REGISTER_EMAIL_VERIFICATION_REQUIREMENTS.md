# 用户站 — 注册邮箱验证码（需求说明）

> **范围**：仅**用户自主注册**（用户站）；与忘记密码链路（[PASSWORD_RESET_REQUIREMENTS.md](./PASSWORD_RESET_REQUIREMENTS.md)）共用 **SMTP、`CaptchaService`、哈希存证**等能力，但**业务语义与安全策略不同**，须独立实现与文案。  
> **数据模型**：[DATABASE_DESIGN.md](./DATABASE_DESIGN.md) §3.12 `registration_email_codes`（与 §3.13 `password_reset_tokens` **分表**）。**本文档不要求与当前已实现行为逐项一致**。  
> **后续**：技术选型（纯 OTP / 魔法链接）、具体接口命名与 TTL 以实现阶段技术设计文档为准。

---

## 1. 背景与目标

| 项 | 说明 |
|----|------|
| **问题** | 现行注册仅靠图形验证码与用户自填邮箱，易出现**刷单号、胡乱填邮箱无法联系、误入他人邮箱**等问题；产品与合规上需要「对该邮箱有可投递权」的简单证明。 |
| **目标** | 用户完成注册前，须通过向**拟定注册邮箱**发送的 **一次性验证码**（或等价可验证凭证）完成核验，再走现有密码哈希、配额写入等步骤。 |
| **成功标准** | 无法在**未读到该邮箱收件**的情况下完成激活式注册（对所选模式而言）；SMTP 不可用时的降级策略产品与运维可见；防刷与隐私策略可验收。 |

---

## 2. 用户故事与边界

### 2.1 本期要做（产品）

| 编号 | 故事 |
|------|------|
| **REG-01** | 用户在注册页输入**邮箱**（及既定字段如密码），可触发「**获取验证码**」。 |
| **REG-02** | 系统在限额内向该邮箱投递一条**短时有效**验证码（推荐使用 **数字/字母 OTP + 可复制粘贴**）；邮件内说明产品与过期时间。 |
| **REG-03** | 用户在同一注册请求（或向导下一步）提交**验证码 + 原注册字段**，校验通过后创建账号并完成登录态发放（或与现有 `/auth/register` 行为对齐）。 |
| **REG-04** | 发信前与用户站其他敏感接口一致：**图形验证码**必选（对齐 `GET /auth/captcha` / 现有登录、忘记密码习惯）。 |

### 2.2 本期不做（可作为二期）

| 编号 | 说明 |
|------|------|
| **REG-N01** | **仅魔法链接**、无 OTP 的流程（可作为替代方案在技术设计选型，本条需求不排斥双模式，但产品上须明确默认路径）。 |
| **REG-N02** | **短信 OTP**、TOTP、「绑定第三方登录后再验证邮箱」等。 |
| **REG-N03** | **管理端**代用户跳过邮箱验证（若需增加，单列变更与审计）。 |

## 3. 功能需求

### 3.1 界面与交互

| 编号 | 需求 | 优先级 |
|------|------|--------|
| **U-REG-01** | 「获取验证码」按钮具备**冷却倒计时**（如 60s），避免重复触发；失败后提示泛化文案。 | P0 |
| **U-REG-02** | 明示验证码 **有效期**（如「约 15 分钟内有效」，与后端配置一致）；支持 **中英文**及其他仓库已采纳 locale。 | P0 |
| **U-REG-03** | 校验失败场景：**错误码/过期**与**剩余可试次数耗尽**有可区分或非泄露式提示（与安全策略 §4 一致）。 | P1 |
| **U-REG-04** | 注册表单保持与现有前端密码策略校验一致（与 `register` 后端对齐），避免双线标准。 | P0 |

### 3.2 服务端业务规则（产品层）

| 编号 | 规则 |
|------|------|
| **B-REG-01** | 验证码与邮箱**绑定**：同一 OTP **不可**交叉用于其它邮箱字段。 |
| **B-REG-02** | 验证码 **一次性消费**：核验成功并完成用户创建后即作废；核验失败可按策略递增限制或作废重发。 |
| **B-REG-03** | **有效期**：默认建议 **10–30 分钟**（可配置），过期须重新获取。 |
| **B-REG-04** | 同一邮箱在**未完成注册**前的重复「获取验证码」：受 **冷却时间与日上限**约束（阈值技术设计给定）。 |
| **B-REG-05** | 完成后将 `users.email_verified_at`（或等价字段）置为核验成功时刻；若历史上允许登录前未验证，本需求实施后**新产品默认**为注册即已验证。 |
| **B-REG-06** | **邮箱已注册**时：不向攻击者暴露「是否存在」为第一原则；产品与实现二选一：**(a)** 对已注册邮箱静默不发注册类验证码但仍返回与时间模糊相关的泛化成功，或 **(b)** 发一封「该邮箱已注册，请登录/找回密码」且无注册侧泄漏——须在技术设计中**写死为一种**并对文案验收。 |

### 3.3 邮件内容（产品侧）

| 编号 | 要求 |
|------|------|
| **M-REG-01** | 含验证码本体或清晰复制区、产品名、为非回复邮件声明、有效期与「若非本人请勿操作」提示。 |
| **M-REG-02** | **不得**在长文本中混入可预测的查询参数令牌替代 OTP，除非与安全评审后的魔法链接方案一致并做好单次消费与过期。 |

---

## 4. 安全与隐私（强制）

| 编号 | 要求 |
|------|------|
| **S-REG-01** | **限流**：对 `email + IP + device 指纹（若有）` 组合限制发信频次；超限返回与不区分原因的**泛化错误**或等价 HTTP 行为，**不泄漏**限速细节给恶意方。 |
| **S-REG-02** | **存储**：验证码仅存**哈希 + 过期时间**，与 `password_reset_tokens` 同源安全级别；日志禁止明文 OTP。 |
| **S-REG-03** | **枚举**：`/register` / 核验接口不得在错误体中直接或间接对比「验证码错」vs「邮箱已存在」的组合导致批量探测；具体要求见 **B-REG-06**。 |
| **S-REG-04** | **SMTP 未启用**：须有明确产品与运维降级（禁用注册入口 / 控制台提示），不得静默失败为空洞注册。 |

---

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| **NF-可观测** | 发信成功率、核销成功率、超限拦截次数聚合（不含 OTP 明文）。 |
| **NF-合规留存** | 验证记录留存周期在技术设计写明； GDPR/个人信息场景下可归因最小化。 |
| **NF-无障碍** | 邮件与页面尽量兼容读屏键位（占位，与全站无障碍策略对齐）。 |

---

## 6. 验收清单（概要）

1. 未验证 OTP（或令牌）无法在常规路径完成具备登录能力的账号落地（与设计选定模式一致）。  
2. 冷却与全局限流可被触发且不导致邮箱存在性或可推断性枚举。  
3. SMTP 拔掉或失败时符合 **S-REG-04** 约定行为。  
4. 中英文（或仓库已支持的 locale）注册全流程文案闭环。
