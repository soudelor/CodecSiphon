# 存储与下载传输计量 / 配额 / 计费 — 需求说明（v0.1）

> **目的**：在「用户下载文件多、占磁盘大」的现状下，把**可执行的规则**与**可演进为商业计费的数据模型**写清楚；与现有 **`users.storage_quota_bytes` / `users.storage_used_bytes`**、`media_files`、`ADMIN_MODULE` 中 U-04 等已实现能力对齐。

---

## 1. 背景与目标

### 1.1 背景

- 本平台以「抓取链接 → Worker 下载 → 落盘 + 入库」为主链路；磁盘与出口带宽随用户规模线性增长。
- 当前已实现用户维度 **存储配额** 与 **已用字节数**（及管理端可调配额）；架构文档约定「超额拒绝新任务或仅告警」等策略可配置，但产品与计费语义尚未收口。

### 1.2 目标（分层）

| 层级 | 目标 |
|------|------|
| **G1 规则收口** | 明确「在什么时机、对谁、按什么口径」校验与拦截，避免只靠运维手工删文件。 |
| **G2 计量可追溯** | 形成可对账、可聚合的计量事件或周期汇总，支撑运营报表与纠纷处理。 |
| **G3 计费可扩展** | 预留「套餐 / 用量阶梯 / 超额单价」等概念，不绑定具体支付渠道；后期可接订阅、储值、发票等。 |

### 1.3 非目标（本期文档不强制落地）

- 具体支付网关、发票、税务、多币种定价。
- 对象存储（S3/OSS）与 CDN 的完整成本分摊模型（可作为后续附录）。

## 2. 术语与计量对象

### 2.1 持久化存储（Storage，已定基线）

- **定义**：用户账号下**仍保留在系统内、占用磁盘（或等价对象存储）**的媒体字节数。
- **主数据口径**（与 `docs/ADMIN_MODULE.md` **U-06** 一致）：
  - **权威业务字段**：`users.storage_used_bytes`（应与 `SUM(media_files.size_bytes)` 可对账）。
  - **配额上限**：`users.storage_quota_bytes`。
- **生命周期**：入库（任务完成写入 `media_files` + 递增已用）、删除文件/任务清理（递减已用）。
- **与「下载量」的关系**：持久化存储是「留下来的部分」；不是每一次 HTTP 流出的总和。

### 2.2 下行传输（Egress / 下载出站带宽）

- **定义**：用户从平台**拉取已保存文件**（如通过 API 拿到的下载链接、流媒体拉取）所产生的**出站字节数**。
- **与 Worker 抓取的区别**：Worker 侧从互联网拉视频属于「入站/inbound」（相对平台机房），与用户侧「从自己站点下载文件」的出口计量不同。
- **现状**：暂无统一计量表；本条为**计费扩展必选维度**，需在实现阶段定义采集点（见 §5）。

### 2.3 抓取传输（Ingress / 远端拉取，可选计量）

- **定义**：Worker 执行 `yt-dlp`（等）从公网拉到本机或服务器的字节量。
- **用途**：更接近「链路成本」，可与出口分开定价或仅作内部成本 KPI。
- **策略**：首期可为 **P2**，若要做「按带宽收费」需明确是否对用户可见计价。

### 2.4 规则与「套餐」（Plan）

- **规则**：在满足某条件时对某动作 **允许 / 拒绝 / 限流 / 告警**。
- **套餐**：给用户绑定一组上限（存储上限、月度出口上限、并行任务数等）及价格属性；可多档（免费 / 会员 / 企业）。

## 3. 与现状的对齐（As-Is）

- **已有**：用户 `storageQuotaBytes`、`storageUsedBytes`；管理端可改配额（允许低于已用量，须显著超额告警）。新用户缺省存储/月下载出站配额可在 **`backend/.env`** 配置（`DEFAULT_USER_STORAGE_QUOTA_BYTES`、`DEFAULT_USER_MONTHLY_DOWNLOAD_QUOTA_BYTES`），见 `.env.example`。
- **已有片段**：Worker 在完成下载后递增 `storage_used_bytes`；删除媒体时扣减（见 `media.service` / `tasks.service` 等）。
- **已有**：`backend/src/storage-policy/`——下载任务创建入队前的策略注册点（当前实现：**硬拒绝**——当 `storage_used_bytes >= storage_quota_bytes` 时拒绝 `POST /tasks`）；便于追加出站带宽、软拒绝或按套餐拆分策略。
- **缺口（待产品/研发在后续迭代选择）**：
  - 失败任务「重试 / 重新入队」等路径是否与新建任务一视同仁执行策略。
  - 出站带宽与抓取流量的计量与限流。
  - 周期性用量汇总与计费科目映射。

## 4. 功能需求

### 4.1 存储配额规则（优先级：P0）

**FR-S1 校验时机（必须写明之一或组合）**

- **推荐默认**：在用户**创建可导致新增持久化字节**的动作前校验（如新任务入库前预估、或 Worker 在开始写入磁盘前复核）。
- **必须兜底**：任一导致 `storage_used_bytes` **增加**的路径，须有统一领域校验，避免仅靠某一入口。

**FR-S2 预估与精度**

- 若创建任务时能拿到**可信预估大小**（解析阶段），则用「预估 + 已用 ≤ 配额」做 **软拒绝或排队**；
- 若无法预估（直播流、可变码率），则采用「写入累计 + 达线即暂停/中止后续写入」的策略，并在需求中定义为 **硬性策略**（需写清用户感知：任务失败原因、是否部分落盘）。
- BigInt / 溢出：配额与字节比较须与数据库类型一致。

**FR-S3 超额后的行为模式（枚举，必选一种为默认）**

- **Mode A**：硬拒绝——禁止新建占用存储的任务；已排队任务可被标记为 blocked（需可查原因码）。
- **Mode B**：软允许 + 告警——允许继续但必须提示「超配额」，并给运营/计费留窗口（不推荐长期作为默认）。
- **Mode C**：宽限期——在超额后保留 T 天内只读下载、禁止新建（需 TTL 与用户通知）。

建议在配置层（全局 + 可按用户层级覆盖）枚举上述模式。

**FR-S4 用户可见性**

- 用户站展示：**已用量 / 配额 / 使用率**（与 `ADMIN_MODULE` 口径一致）；接近阈值（如 80%、95%）时提示。
- 与现有前端「存储规划中」占位（`storagePlanned`）对齐：**本期需求应要求替换为真实数据**。

**FR-S5 管理与审计**

- 管理端继续使用现有 PATCH `storageQuotaBytes`；须在操作审计中保留「谁在何时把配额改成多少」（若尚无字段则单列任务）。

---

### 4.2 出站下载带宽 / 传输量规则（优先级：P1，计费前置）

**FR-B1 计量粒度**

- 最小建议：**每次成功下发的字节数**聚合到「用户 × 自然日 × 计费科目」；
- 需排除：健康检查、静态资源（若同源）、管理端导出（可按角色分流不计费）。

**FR-B2 限流 vs 计费**

- **限流**：峰值带宽或 QPS（保护服务器与上联）——可与「套餐」绑定。
- **计量**：按月累计字节，用于超额计价（可以与限流策略独立）。
- **必须约定**：超限时的 HTTP 语义（429 + `Retry-After`？或限速而不拒绝？）。

**FR-B3 公平性**

- 单用户并发下载连接数、单文件最大吞吐（可选）。

---

### 4.3 抓取侧（Ingress）规则（优先级：P2，可选）

**FR-I1**：是否将 Worker 远端拉流量计入「用户用量」须有明确口径（默认建议：**仅内部成本 KPI**，不向用户显性计费除非产品明确要求）。

---

### 4.4 套餐与规则引擎（优先级：P1）

**FR-P1**：定义「套餐」实体（可先简化为配置表或 JSON），字段至少包含：

- `storageQuotaBytes`
- （可选）`monthlyEgressBytes` — 月度出站累计上限
- （可选）`maxConcurrentDownloads`、`maxQueuedTasks`

**FR-P2**：用户与套餐绑定关系（`user.plan_id` 或等价）；注册默认套餐可配置。

**FR-P3**：规则执行顺序：**平台全局硬上限** > **套餐上限** > **用户单独 override（管理端特例）**。管理端特例须审计。

---

### 4.5 计费扩展（优先级：P2）

**FR-C1**：用量沉淀为**不可变月度账单行**或对账快照（账单期、科目、quantity、单价、币种、快照时间）。

**FR-C2**：科目建议初始集合：

| 科目代码 | 说明 |
|-----------|------|
| `STORAGE_BYTES_DAY` | 可选：日均存储字节·天（更接近云厂商模型） |
| `STORAGE_MAX_BYTES` | 峰值或期末占用（更简单） |
| `EGRESS_BYTES` | 出站累计字节 |

（首期可先仅 `STORAGE_MAX_BYTES` + `EGRESS_BYTES`，避免过度工程。）

**FR-C3**：与套餐关系：阶梯价（超过包含量后单价）、封顶价等以**附录**列出，不落库细节可在计费服务实现。

---

## 5. 非功能需求

- **NFR-1 一致性**：`storage_used_bytes` 与 `media_files` 聚合的差异须有说明与周期性对账脚本（或管理端一键对账）。
- **NFR-2 性能**：配额校验在用户热路径内需 O(1) 读缓存或单行读；忌全表聚合。
- **NFR-3 可观测性**：被拒原因须有稳定 `error_code`（便于前端/i18n/客服）。
- **NFR-4 隐私与合规**：用量属于个人数据摘要；计费明细保留周期符合公司政策。

---

## 6. 验收清单（概要）

- 超配额用户在所选默认策略下行为符合 §4.1；
- 用户站可展示真实存储用量；
- （若做 P1）出站计量与「超限行为」可查可对账；
- 管理端改配额 / 超额提示与 ADMIN 文档一致。

## 7. 待产品拍板事项（Open Questions）

1. 默认超额策略：**Mode A/B/C** 选哪一个？
2. 无法在创建时预估大小的任务：**是否允许部分落盘后失败**，还是一律预先拒绝？
3. 出站计费是否纳入 **P1**：若带宽成本高，建议升 P1。
4. 「存储计费」更接近 **占用峰值**还是 **字节·日**？
5. 免费用户是否有 **硬性全局上限**（防滥用），与注册用户区分？
